# Тестовое Neowise. AI-помощник для входящих заявок

Ориентир — 45–60 минут. Менеджер вводит текст заявки, получает тему и черновик ответа. Он читает результат и сам решает, что отправить клиенту.

## Запуск

В репозитории есть сервер, HTML-страница и имитатор модели. Нужен Node.js 20 или новее. Зависимостей и ключей нет.

```sh
node server.mjs
```

Откройте http://127.0.0.1:3000. Порт можно задать через переменную `PORT`.

## Контракт задания

1. Доработайте `POST /api/triage`. Принимайте JSON с полем `text`, содержащим непустую строку. При пустом, отсутствующем, нестроковом вводе или битом JSON верните HTTP 400 и `{"status":"invalid_input"}`.
2. При корректном ответе модели верните HTTP 200 и `{"status":"ready","topic":"…","draft":"…"}`. Допустимые темы — `delivery`, `pricing`, `other`. Черновик должен быть непустой строкой. При таймауте, ошибке модели или неподходящем ответе верните HTTP 200 и `{"status":"manual_review","topic":null,"draft":null}`. Ограничьте ожидание модели 300 мс. Оставьте поведение выданного имитатора прежним.
3. Покажите на странице тему и черновик при успехе. Для `manual_review` покажите понятное сообщение менеджеру и очистите предыдущий черновик. Добавьте хотя бы один исполнимый тест для поведения при сбое и инструкцию его запуска.

Для локальной проверки имитатор принимает любой обычный текст. Метки `[timeout]`, `[error]`, `[bad-json]`, `[bad-topic]`, `[empty-draft]` включают отдельные сценарии сбоя.

## Что прислать в бота

- Ссылку на pull request и SHA проверяемого коммита. Можно использовать свой учебный репозиторий. Сохраните начальный код первым коммитом, затем откройте PR из отдельной ветки.
- Короткую инструкцию запуска и прогона теста. В описании PR ответьте, где проверяется результат AI, что происходит при сбое, какой AI вы использовали и что проверили самостоятельно. Если работали без AI, укажите это.
- Одну фразу о том, какую пользу задача даёт менеджеру и как её можно измерить.

После сдачи бот может задать один-два коротких вопроса по вашему коду. Используйте учебные данные. Если не уложились по времени, отметьте незавершённые части в PR.

## Что реализовано

- Ввод проверяется до обращения к модели: битый JSON, отсутствующее поле, неверный тип и строка из пробелов получают `400 invalid_input`.
- В `server.mjs` результат модели проверяется после JSON-разбора через `isReadyResult`: только `delivery`, `pricing`, `other` и непустой черновик после `trim()`.
- Таймер на 300 мс вместе с `Promise.race` ограничивает ожидание; `AbortController` отменяет работу исходного имитатора. Таймер очищается после завершения. Если внешний провайдер игнорирует отмену, API всё равно не ждёт его бесконечно; фактически остановить такого провайдера клиентским signal нельзя.
- Ошибки модели, таймаут и неверный результат дают ровно `200 {"status":"manual_review","topic":null,"draft":null}`. Имитатор `mock-ai.mjs` не изменён.
- На странице показаны понятные состояния. При сбое менеджер видит исходный текст, выбирает тему и пишет ответ вручную. Прежний черновик очищается уже при новом запросе. Автоматической отправки клиенту нет.
- `requestId` защищает от ответов в обратном порядке, включая запоздалые ошибки. Изменение исходного текста тоже делает старый ответ неактуальным. Отдельный клиентский дедлайн 5 секунд защищает от недоступного API.
- Контент модели записывается в `value`, сообщения — в `textContent`; HTML модели не исполняется.

## Тесты

Node.js 20+, без установки зависимостей:

```sh
node --test --test-concurrency=1 triage.test.mjs
```

Тесты поднимают временные HTTP-серверы только на `127.0.0.1` со свободным портом и закрывают их после проверки. Внешние API и платные модели не вызываются.

Проверяются настоящий HTTP-контракт, все пять меток исходного имитатора, зависший провайдер, неправильные типы ответа, очистка старого черновика, сетевые ошибки и порядок A/B. Клиентская логика проверяется без браузера; визуальный осмотр страницы описывается отдельно в PR, а не засчитывается этими тестами.

Для ручной проверки: сначала введите «Когда доставка?», затем по очереди метки сбоя. При каждом сбое черновик должен стать пустым, а поля ручного разбора — остаться доступными. Очистите поле или оставьте пробелы: должно появиться сообщение о неверном вводе.

## Польза менеджеру

Менеджер получает заготовку для обычной заявки, а при сбое сразу продолжает работу вручную и не отправляет случайно устаревший черновик. Пользу можно измерить временем обработки заявки **с учётом проверки и исправлений**, долей ручного разбора и количеством ошибочных ответов относительно работы без помощника. Фактических бизнес-замеров в учебном задании нет.

## Использование AI и границы решения

Решение и тесты подготовлены с помощью Codex. Проверено на Node.js 22.20.0: команда выше завершилась успешно, 36 проверок, 0 ошибок (включая вложенные сценарии). В браузере проверены успешная заявка, пустой ввод, переход от готового ответа к пустому черновику при `[empty-draft]`, ручное редактирование и `[timeout]`. Визуальные проверки выполнены агентом; отдельная пользовательская приёмка не заявляется.

Это локальный учебный стенд без БД, авторизации и отправки писем. Текст заявки остаётся в текущей странице, но не сохраняется между перезагрузками. Для production отдельно потребуются ограничения размера запросов, журналирование, метрики и хранение заявок.
